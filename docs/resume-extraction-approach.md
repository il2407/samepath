# Resume extraction: pipeline audit, OCR evaluation, and the deterministic-vs-AI decision

Written for WS1 (registration and résumé flow). Covers three backlog items:
auditing/improving the current PDF/DOCX extraction pipeline, evaluating OCR
for scanned resumes, and evaluating deterministic vs. AI-backed structured
extraction. The provider-agnostic `ResumeParser` interface this evaluation
feeds into lives in `src/modules/resumes/parser.ts` — its doc comment
carries a shorter version of the same conclusion; this file is the full
writeup.

## 1. Pipeline audit: what was there, what changed

Before this pass: `text-extraction.ts` called `pdf-parse` (PDF, via
`pdfjs-dist`) or `mammoth` (`.docx`) and returned their raw output
unmodified. `deterministic-parser.ts` regex-scanned that raw text for
date-ranged employment positions and known skill/language labels.

Real, fixable gaps found and addressed in this pass:

- **Encoding artifacts.** Some PDF/DOCX generators emit accented and Hebrew
  text as a base letter followed by separate Unicode combining marks
  (decomposed/NFD form) rather than one precomposed codepoint (NFC) — same
  rendered appearance, different code points, which silently broke the
  parser's exact-substring label matching (a skill/language/region label
  that visually matches but fails a `===`/`includes` check). Fixed by
  NFC-normalizing text at both extraction (`text-extraction.ts`) and parsing
  (`deterministic-parser.ts`, so the pure parser is robust regardless of
  caller).
- **Copy-paste-from-Word artifacts.** Non-breaking spaces (`U+00A0`) are
  common in DOCX exports and don't match a plain space in whitespace-aware
  matching — normalized to regular spaces.
- **Stray control characters** some PDF generators leave embedded in text
  runs — stripped (tab/newline preserved).
- **No signal for "this file has no text at all."** `pdf-parse` returning
  empty/near-empty text (the scanned-PDF case, see §2 below) and a
  genuinely broken extraction previously produced the same generic "failed"
  state. Added `looksLikeEmptyTextLayer()` so the two get different,
  specific Hebrew messages (see `resumes/service.ts`'s `runExtractionJob`
  and `ResumeUploadCard.tsx`).
- **Heuristic coverage.** The parser previously surfaced positions, a
  current-role guess, matched skill/domain tags, and matched languages, but
  left `professionalFieldId`, `regionId` (location), and `shortIntro`
  (summary) hardcoded blank on every resume upload regardless of what the
  file actually contained. Added, all following the same "exact known-label
  match, or a narrowly-scoped single-line heuristic — never a guess
  presented as fact" discipline as the existing skill matching (language
  matching has since been removed along with the language factor itself):
  - **Target role / professional field**: matching a known `TargetRole`
    label (e.g. "Backend Developer") in the text now also selects that
    role's `professionalFieldId` — safe because a target role belongs to
    exactly one field, so this is a lookup, not an inference.
  - **Region (location)**: matching a known `Region` label the same way.
    Single-select (the field's `regionId` is not multi-value), so at most
    one match is returned.
  - **Short intro (summary)**: a heuristic that looks for a recognized
    summary/about heading (`תקציר`/`תמצית`/`אודות`/`על עצמי`/`פרופיל אישי`/
    `summary`/`about`/`profile`/`objective`) and, only if found, drafts the
    intro from the line immediately following it — never from arbitrary
    prose elsewhere in the document. Returns `null` (not a fabricated
    sentence) whenever no such heading exists or the following line is too
    short to plausibly be real content.
- **Temporary files: none exist, confirmed.** Checked whether `pdf-parse`
  (`pdfjs-dist`) or `mammoth` ever write to disk during extraction — neither
  does; both operate purely on the in-memory `Buffer` passed in. There is
  nothing to clean up on this path today (the backlog item asking to verify
  this is addressed by this finding, not by new cleanup code). If a future
  OCR step or a different library changes this, whatever calls it must use
  a `try/finally` to guarantee deletion on every exit path, matching the
  discipline already used for resume storage deletion in
  `resumes/service.ts`.

## 2. OCR evaluation (scanned/image-only PDFs)

A **scanned PDF** — a photo or flatbed scan of a paper resume, or a PDF
generated by "print to PDF" from a scanner — has no text layer at all: the
page is just an embedded image. `pdf-parse`/`pdfjs` can only read an actual
text layer; there is nothing for it to extract, so it returns empty or
near-empty text rather than throwing. This pass adds detection for that
case (`looksLikeEmptyTextLayer`) and a specific, useful Hebrew message
("this looks like a scanned file, not text — try a different file or fill
in manually") instead of a generic failure. It does **not** implement OCR
itself. Evaluated and deliberately not pursued, for now:

- **What it would take**: a real OCR engine (e.g. Tesseract via a wrapper
  package, or a cloud OCR API) to rasterize each PDF page and recognize
  text from the image. This is a materially heavier dependency than
  anything else in the resume pipeline — Tesseract's language data alone is
  tens of megabytes per language (Hebrew + English both needed here), and
  it typically wants a native binary or WASM runtime, not just an npm
  package.
- **Cost/latency**: OCR is slow relative to this pipeline's "run inline in
  the same request" design (architecture-decisions.md #9) — seconds per
  page, not milliseconds — and a cloud OCR API reintroduces the exact
  privacy/cost tradeoffs discussed for AI parsing in §3 below (a scanned
  resume's content leaving this process to a third party).
  Deterministic OCR output would then still need to go through the exact
  same deterministic-parser heuristics to become structured fields — OCR
  only solves "get text out of the image," not "understand the resume,"
  and OCR text is also often noisier (misread characters) than a native PDF
  text layer, which could make the deterministic parser's exact-label
  matching *less* reliable, not more.
- **How common is this case, really?** Scanned resumes are the minority
  case for a product whose users are actively job-searching and producing
  polished, computer-generated documents (Word/LaTeX/resume-builder
  exports) — not scanning paper resumes. The generic PDF/DOCX path already
  covers the overwhelming majority of real uploads.
- **The safety net that already exists**: manual entry
  (`ProfileStepOneForm`) is always available and never blocked by a failed
  or scanned-file extraction — a user who hits this case loses nothing
  except the auto-fill convenience, and now gets a message that tells them
  *why* and what to do next instead of a generic failure.

**Recommendation**: do not add an OCR dependency for this MVP. Revisit if
real usage data shows a meaningful fraction of uploads are scanned
image-only PDFs (something to actually measure — `ResumeExtractionJob.error`
already distinguishes `EMPTY_TEXT_LAYER` failures from other failures,
so counting them is a query away, not a new instrumentation project) and
the manual-entry fallback turns out to be a real drop-off point.

## 3. Deterministic vs. AI-backed structured extraction

**Hard constraint for this pass** (product/security requirement, not an
engineering preference): no real network call to an AI/LLM API, no live use
of `RESUME_AI_API_KEY`, no new AI-provider SDK dependency requiring real
credentials. There is no API key available in this environment and this
task must not attempt to reach an external AI service. The evaluation below
is a genuine comparison, not a formality — but its purpose is to justify
*not* building one right now, and to design `ResumeParser`
(`src/modules/resumes/parser.ts`) so a real AI adapter could be dropped in
later without an interface change.

Options considered:

| | Cost | Latency | Privacy | Accuracy | Ops complexity |
|---|---|---|---|---|---|
| **Deterministic (wired)** | Free | Milliseconds | Never leaves this process | Good on well-formatted resumes; misses education, abstractive summaries, unusual layouts | None — pure function, no new infra |
| **Local/self-hosted AI model** | Server compute (GPU/CPU time) | Seconds | Stays on our infra, not a third party | Likely better than deterministic on messy input | Real — a model-serving process to deploy, monitor, and update; against this codebase's explicit "no second process to operate" philosophy (architecture-decisions.md #9) |
| **In-browser AI model** | Client compute, one-time model download (often 100s of MB) | Seconds, plus first-load download | Best — never leaves the user's machine | Similar to local, constrained by what fits in a browser tab | Real — bundling/versioning a client-side model runtime is new infra this MVP doesn't have anywhere else |
| **Claude API (or similar hosted LLM)** | Real per-call $ cost, scales with signups | Seconds (network + inference) | Résumé content (employer, titles, dates, sometimes contact info) leaves this process to a third party | Likely the best of these options on messy/unusual resumes; could plausibly fill fields deterministic parsing structurally can't (education, real abstractive summaries) | Low to add (an SDK call) but real: billing, rate limits, error handling for a third-party dependency in the critical upload path |
| **Hybrid** (deterministic first, AI only for fields left empty) | Only pays AI cost on resumes that need it | Same order as pure AI, but only for a subset of uploads | Same objection as pure AI, but scoped to a subset of content/uploads | Best of both — free/instant common case, AI-assisted long tail | Same real cost as pure AI, just less of it |

Reasoning behind the recommendation:

- **Cost & latency** favor deterministic decisively for the common case:
  free, instant, and consistent with "no background job queue — résumé
  extraction runs synchronously inline" (architecture-decisions.md #9). Any
  AI option reintroduces exactly the kind of latency/ops tradeoff that
  decision explicitly avoided elsewhere in this codebase.
- **Privacy** is the strongest objection to a hosted AI option specifically
  for *this* product: SamePath's own premise is discretion (README: "a
  discreet professional community for people navigating similar job
  searches"). `ResumeUploadCard` already tells users their file and
  extracted data "are stored only in our system — not sent to any
  third-party service, not exposed to any company or agency." Wiring a real
  AI API call would make that specific, user-facing promise false. This
  objection doesn't apply to local/in-browser AI, but those bring their own
  real infra cost instead (see below).
- **Accuracy** is a genuine point *in favor* of AI — not a strawman to wave
  away. An AI parser would very plausibly do better on messy or unusually
  formatted resumes, and could fill fields the deterministic parser
  structurally cannot reach at all (education — there's no schema field for
  it yet either, see the "Known limitations" note in the code — and a truly
  abstractive summary rather than a lifted sentence). But the product
  already treats every extraction as a *draft*: `ResumeDraftReview` wraps
  the exact same `ProfileStepOneForm` used for manual entry, and nothing is
  written to a real profile until the user reviews and confirms it. Under
  that design, the deterministic parser's lower recall costs the user "fill
  in one more field, or leave it blank" — a small, honest, visible cost.
  An AI parser's failure mode is different and worse for this product:
  a *wrong-looking, confident* value that's easier to skim past unverified,
  in a product whose entire matching quality depends on people trusting
  what's in a profile. This is the same reasoning behind the account-wide
  rule against ever presenting unverified information as fact, applied here
  to extracted résumé fields specifically (see backlog items 9–11: never
  show a guessed placeholder as if it were found data, and distinguish
  "nothing found" from "found, please double-check" in the UI —
  implemented in this pass via `ResumeDraftReview`'s extraction summary).
- **Local/in-browser AI** solve the privacy objection but trade it for a
  different real cost: genuinely new infrastructure (a model-serving
  process, or a client-side inference runtime) that this MVP doesn't run
  anywhere else, for a product decision (résumé auto-fill quality) that
  doesn't obviously justify that operational commitment yet.
- **Hybrid** is, honestly, the most promising *future* direction: keep the
  free/instant/local deterministic pass as the default for every upload,
  and only reach for an AI call — with real cost, latency, and privacy
  exposure — for the specific fields it left empty (education, a real
  summary) on resumes that actually need it. This is explicitly not
  implemented here: it still needs a real provider decision, a budget, rate
  limiting, and — because it's a genuine privacy-relevant capability change,
  not a drop-in swap — an explicit user-facing disclosure ("this field was
  filled in with the help of an AI service") that doesn't exist anywhere in
  this MVP today.

### Recommendation

Keep the deterministic parser as the wired default
(`RESUME_PARSER=deterministic`, unchanged in `.env.example`). Invest
further effort in its heuristics and test coverage — this pass added
target-role, region, and short-intro detection with unit and integration
coverage — rather than reaching for AI. Leave `AiResumeParser`
(`src/modules/resumes/parser.ts`) as a documented, swappable, **not wired**
placeholder that throws on construction (matching the existing
`S3Storage`-not-implemented pattern in `src/shared/storage.ts`) for whenever
a real provider, a budget, and a privacy-disclosure story exist. This
pass adds no AI-provider SDK dependency and makes no network call to any
AI/LLM API.

## Known limitations of this pass

- **Education** is not extracted. There is no `education` field anywhere in
  `ProfessionalProfile` or the `ProfileStepOneInput`/`ProfileStepOneForm`
  shape today — the product's onboarding form itself doesn't ask for it —
  so there's nowhere for an extracted value to go without a schema
  migration, which is out of scope for this workstream (see the WS1
  instructions: "no DB schema changes are expected"). Flagged here as an
  integration request for whichever workstream owns onboarding-field scope
  changes, not implemented speculatively.
- **`professionalFieldIdGuess`** is only ever set when a known `TargetRole`
  label matches verbatim in the text; a resume phrased entirely differently
  from the seeded role taxonomy (e.g. a title in a language/phrasing not in
  `TargetRole.labelHe`/`labelEn`) gets no guess, by design — a false "no
  signal" is always preferred here over a wrong-looking confident guess.
- **The short-intro heuristic** only ever looks at the single line
  immediately following a recognized heading. A genuine multi-line summary
  paragraph will only have its first line captured. This is a deliberate
  simplicity/safety tradeoff (see the code comment on
  `extractShortIntroGuess` in `deterministic-parser.ts`) rather than an
  oversight — pulling in more lines without a clear paragraph boundary (blank
  lines are already stripped before this heuristic runs) risks grabbing
  unrelated content from the next section.
- **Hebrew text through the synthetic PDF test fixture**
  (`__tests__/pdf-fixture.ts`) is not exercised end-to-end in tests: the
  fixture writes text through a base Helvetica font with single-byte
  Latin-1 encoding, which cannot represent Hebrew glyphs or arbitrary
  Unicode at all (there's no embedded font or `ToUnicode` CMap). NFC
  normalization and Hebrew label matching are instead verified directly
  against the pure parser (`deterministic-parser.test.ts`), and DOCX (which
  handles Unicode natively via mammoth) was not similarly fixture-tested
  because building a valid minimal `.docx` (a ZIP container) from scratch
  without an existing zip dependency in this repo was judged not worth a
  new dependency for a test fixture alone. Manual verification with a real
  Hebrew PDF/DOCX resume is recommended before relying on this in
  production — see the final report's "manual verification still required."
