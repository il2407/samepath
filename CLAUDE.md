## Commands

```bash
pnpm dev                        # start dev server (localhost:3000)
pnpm build                      # production build
pnpm typecheck                  # next typegen && tsc --noEmit
pnpm lint                       # eslint

pnpm test                       # vitest run — full suite, sequential (see below)
pnpm test:watch                 # vitest watch mode
pnpm vitest run path/to.test.ts # single file
pnpm vitest run -t "test name"  # single test by name

pnpm e2e                        # playwright test, against the seeded dev DB
pnpm e2e:ui                     # playwright interactive UI mode

pnpm db:migrate                 # prisma migrate dev
pnpm db:seed                    # prisma/seed.ts
pnpm db:studio                  # prisma studio
```

Local Postgres: `npx prisma dev` (see README "Local development setup" for
exact flags) needs **two separate named instances** — one for `.env`, one
for `.env.test` — because `prisma dev`'s embedded engine doesn't isolate
same-instance databases from each other. Docker Compose is the alternative
and doesn't have that restriction. `.env.example` / `.env.test.example`
document every variable and which adapter it selects.

Integration tests run against the real `.env.test` database and `TRUNCATE`
it between tests, guarded to refuse running unless `DATABASE_URL` contains
`samepath_test`. Because of that shared reset, `vitest.config.ts` sets
`fileParallelism: false` — test files run one at a time, deliberately.

## Architecture

A modular monolith. Every domain lives under `src/modules/<name>/` with the
same internal shape, consistently:

- **Pure logic files** — no DB, no framework import, fully unit-testable,
  importable from plain scripts (e.g. `prisma/seed/*.ts`). This is where the
  privacy engine, scoring, parsers, and reward math live.
- **`service.ts`** — `server-only`, the real DB-backed logic.
- **`actions.ts`** — `"use server"`, thin zod validation that calls into
  `service.ts` and owns cookies/redirects/revalidation. Nothing else should
  touch cookies/redirects directly.
- Client components (`.tsx`) for anything interactive.

When adding a feature, follow that split rather than putting DB calls or
framework concerns into the pure logic files — it's what keeps the
privacy/scoring/parsing logic exhaustively unit-testable without a database.

Modules (`src/modules/`): `auth`, `profiles`, `resumes`, `companies`,
`privacy`, `matching`, `connections`, `groups`, `guides`, `interviews`,
`moderation`, `credits`, `access-passes`, `payments`, `account`, `admin`,
`reference-data`, `notifications`, `integrations/jobtracker` (types-only,
unwired). See the README's module table for what each one owns.

`src/app/` is routes only (`app/` = authenticated app shell, `admin/` =
`MODERATOR`/`ADMIN`-gated area, `_marketing/` = logged-out landing page,
`api/` = the few things that must be real HTTP routes: OAuth callbacks,
account export, the matching cron endpoint). Route handlers should stay
thin and delegate to `modules/*/service.ts` or `actions.ts`.

`src/shared/` is cross-module infra: `db.ts` (Prisma client via
`@prisma/adapter-pg` — driver adapter is required, not optional, in Prisma
7), `env.ts`, `storage.ts` (`Storage` interface + local-disk adapter),
`rate-limit.ts` (in-memory, single-instance only), `test/` (integration
fixtures, DB reset/guard helpers), `ui/` (shared components).

### Privacy model — the one invariant that must never regress

Enforced in `src/modules/privacy/engine.ts`, a pure function with zero DB
access: never match same-company, never match a blocked company (with
opt-in corporate-group cascade), never match users who've blocked each
other, no public profile browse/search anywhere. Rejections are logged to
`PrivacyDecisionAudit` (admin/test-only, no user-facing reader) — the
*reason* a candidate was hidden is never exposed to either user.

Progressive disclosure lives in `src/modules/profiles/dto.ts`:
`toPreMatchDTO`/`toPostMatchDTO` are pure functions whose pre-match return
type structurally cannot carry name/contact fields (not a filter that could
be forgotten — the fields aren't in the type). The one pre-match exception
is `company`, gated behind the *profile owner's* `shareCompanyPreMatch`
preference (default off) — never the viewer's preference. Every other
optional post-match field follows the same "owner's own preference gates
it" rule. Any new PII-adjacent field on a candidate/user DTO needs the same
treatment — see architecture-decisions.md #7 and #10 before adding one.

### Matching pipeline

Always hard-filter (privacy engine) before scoring — a pair that fails the
filter never reaches `scoring.ts`. Scoring is pure
(`DEFAULT_SCORING_WEIGHTS`) and produces both a score and
`generateSafeReasons()` output that never leaks privacy-sensitive info.
Mutual opt-in is a state machine (`MatchStatus`): `PROPOSED ->
INTERESTED_BY_A/B -> MUTUALLY_ACCEPTED -> ACCESS_CHECK -> ACTIVE`, with
`DECLINED`/`EXPIRED` off-ramps; `ACCESS_CHECK` is the access-pass gate.

Suggestion generation also runs from a real scheduled job
(`src/modules/matching/job.ts#runMatchingJob`, hit via
`src/app/api/jobs/matching/route.ts`) — it calls the exact same
`generateSuggestionsForUser` the in-app button calls, so any change to
scoring/privacy/creation logic must live in `matching/service.ts`, not be
duplicated in the job. See `docs/scheduled-jobs.md`.

### No background job queue

Everything that's conceptually "at some future time, do X" (interview
publication delay, access-pass expiry, stale match-suggestion expiry) is
instead checked/promoted lazily at the top of whatever read/write path next
touches that resource — no scheduler, no worker process. The one job that
genuinely can't follow that pattern is matching (see above), because it
needs to act on users who never open the app again. If you add a new
due-date concern, default to the lazy-check pattern unless it has the same
"nobody will trigger it by visiting" property matching has.

### Adapters (swap points for real integrations)

Every external integration is an interface with a local/fake implementation
— `notifications/mailer.ts` (`Mailer`), `shared/storage.ts` (`Storage`,
S3 branch throws "not implemented" by design), `payments/provider.ts`
(`PaymentProvider`, fake-only — real payments require explicit approval per
the build brief, not just flipping an env var), `resumes/malware-scan.ts`
(`MalwareScanner`, always-clean no-op), resume parsing
(deterministic heuristic parser vs. an `ai` mode). Controlled by env vars
documented in `.env.example`. Don't wire a real implementation in without
checking `docs/security-hardening.md` and the README's "Deployment
requirements" section first.

### Reference data as rows, not enums

`ProfessionalField`, `TargetRole`, `SeniorityBand`, `Language`, `Region` are
DB tables (`reference-data` module), not Prisma enums — new values must be
addable without a migration. Skills/domains/interview-topics share one
`Tag(kind: SKILL | DOMAIN | TOPIC)` table with per-owner join tables. Don't
reintroduce enums for these; do add a new enum for a genuine fixed lifecycle
state (that pattern — `MatchStatus`, `ExperienceStatus`,
`AccessPassStatus`, `PaymentStatus` — is deliberate, per
architecture-decisions.md #8).

### pdf-parse / Turbopack gotcha

`pdf-parse` (via `pdfjs-dist`) resolves its worker relative to its own file
at runtime, which breaks if Turbopack bundles it into a server chunk.
`next.config.ts` keeps it out via `serverExternalPackages: ["pdf-parse"]`.
If you see "Setting up fake worker failed" in the server log, check that
config entry first, don't add a workaround elsewhere.
